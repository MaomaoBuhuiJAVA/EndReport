## 三、本次讲解目的与课程流程

本课不以“如何使用科小贝”为主，而是拆开一个真实 AI 教育网站的开发过程。结束时，听众应能回答以下问题：

1. 为什么不能只做一个聊天框；
2. 怎样把科学诗、故事、实验、图片、视频和二维码变成结构化数据；
3. 前端页面、后端 API、数据库、文件存储和 Dify 工作流如何协同；
4. 文本大模型、视觉模型、图像生成模型分别做什么；
5. 为什么模型密钥不能放在浏览器；
6. 如何把项目从本地推送到 GitHub，再发布到阿里云 ECS；
7. 如何处理超时、模型失败、错误链接、隐私和结果审核。

### 本课要传达的核心观点

> AI 项目最难的部分通常不是“调用一次模型”，而是让模型回答有依据、让资源链接可用、让文件能下载、让失败有回退、让密钥和儿童资料不泄露。

## 四、先讲一个“localhost”案例：为什么本机能打开，别人却打不开

### 1. 现场引入话术（约 3 分钟）

“在项目交流里，我经常遇到这样一种情况：有人说自己已经开发好了网页，打开 ‘http://localhost:3000’ 也能正常使用；但把这个地址发给别人后，对方却打不开。问题不是网页一定写错了，而是 ‘localhost’ 的含义被误解了。

‘localhost’ 指向的是‘正在使用这台电脑本身’。我在自己的电脑上输入 ‘localhost:3000’，浏览器会找到我自己电脑上正在运行的开发服务器；另一位老师在她的手机或电脑上输入同一个地址，找到的却是她自己的设备，而不是我的电脑。因此，本地能打开，只能证明开发环境启动了，不能证明网站已经完成交付。”  

### 2. 用一张图讲清三种访问范围

~~~text
开发阶段：开发者电脑
浏览器 ──> http://localhost:3000 ──> 本机 Next.js 开发服务器
                                      只有这台电脑默认能访问

临时联调：同一局域网
手机/电脑 ──> http://开发机内网 IP:3000 ──> 开发服务器
             还受网络、防火墙、端口和开发服务器监听地址限制

正式交付：公网域名
任意浏览器 ──> https://www.example.com ──> 阿里云 ECS 上的 Next.js 网站与 API
                                              ├─ PostgreSQL 数据库
                                              ├─ 阿里云 OSS 文件存储
                                              └─ Dify 与模型服务
~~~

### 3. “localhost”不能直接变成线上产品的原因

| 缺少的部分 | 本地开发时的状态 | 正式上线后如何解决 |
|---|---|---|
| 可访问地址 | 只有开发机认识 localhost | 绑定公网域名，通过 HTTPS 访问 |
| 稳定运行环境 | 关闭终端或电脑休眠，服务就停止 | 阿里云 ECS 通过 systemd 持续运行网站服务 |
| 数据库 | 可能是本机临时数据或开发库 | 使用线上 PostgreSQL/Neon，按连接串访问 |
| 图片、视频、文档 | 可能散落在开发机磁盘 | 存入阿里云 OSS，由网站服务按权限读取 |
| 密钥 | 容易临时写在本地 .env.local | 配置在 ECS 服务端运行环境中 |
| 团队协作与版本 | 代码只在一台电脑上 | GitHub 保存版本、代码评审与发布记录 |

### 4. 从代码到线上网站的完整关系

~~~text
开发者在本机编写 Next.js / React 代码
              │
              ▼
git commit + git push
              │
              ▼
GitHub：保存可追溯的源代码版本
              │ 自动触发
              ▼
阿里云 ECS：运行 Next.js 网站与服务端 API
       │
       ├─ 读取服务端环境变量：模型、数据库、OSS 等密钥
       ├─ 访问 PostgreSQL：保存结构化资源与业务数据
       └─ 访问阿里云 OSS：读取图片、视频、文件与生成封面
       ▼
公网域名：任何老师通过 HTTPS 打开同一套正式服务
~~~

这里需要特别讲准确：**阿里云 ECS 不是数据库或对象存储。** 本项目的业务数据由 PostgreSQL 保存，图片、视频和文件由阿里云 OSS 保存，ECS 负责运行 Next.js 网站与服务端接口。Dify 也不是直接读取全部数据库和视频文件，它使用整理后的教学文本知识库；网页服务端再把数据库中真实的资源、视频、二维码和详情入口关联回来。

### 3. 前端怎么把“点击”变成请求

打开 [`src/components/SciencePet.tsx`](../src/components/SciencePet.tsx)。它是一个客户端组件，负责：

- 保存消息列表、当前输入、附件和会话编号；
- 文字模式与语音模式切换；
- 把图片或文档放入 `FormData`；
- 调用 `/api/ai-chat`；
- 读取流式事件并逐步更新“正在思考”和回复气泡；
- 渲染 `labLinks`、下载文件、视觉结果和复制/朗读按钮。

补充一个容易被忽略的实现细节：浏览器会随请求带上展示用历史记录，但当前主聊天路由实际依靠 Dify 返回的 `conversation_id` 维持多轮上下文，并没有把浏览器历史全文重新拼进 Dify 请求。这能减少旧消息重复占用上下文；一旦走本地回退，前端会清除旧的远端会话 ID，避免后续问题被过期上下文污染。

可以展示这一段经过简化的真实请求逻辑：

```ts
const response = await fetch("/api/ai-chat", {
  method: "POST",
  headers: { Accept: "text/event-stream" },
  body: formData ?? JSON.stringify({
    message: content,
    userId: difyUserId,
    conversationId: difyConversationIdRef.current,
  }),
});

const data = await readAiChatResponse(response, onEvent);
```

讲解重点：浏览器只认识自己的 `/api/ai-chat`，而不知道 Dify 密钥、DeepSeek 密钥或数据库密码。这是前后端分层的第一条原则。

## 七、数据建模与资源入库：47-60 分钟

### 1. 为什么不能把所有内容塞进一个 Markdown

需要把“可供模型阅读的文字”与“真实业务资源”区分开：

| 数据 | 存放位置 | 原因 |
|---|---|---|
| 科学诗正文、实验说明、年龄段、主题 | JSON / PostgreSQL / Dify Markdown | 便于检索、摘要和模型引用 |
| 视频、步骤图片、二维码、封面 | 阿里云 OSS 或站点公开静态资源 | 文件体积大，需要稳定 URL 和缓存 |
| 资源与媒体的对应关系 | PostgreSQL `ScienceKnowledgeResource` | 保证“同一实验的图片、视频、二维码”不会串到别的实验 |
| 用户、管理员权限、园所资料 | PostgreSQL | 需要权限与业务查询 |
| 多轮会话编号 | 浏览器状态 + Dify `conversation_id` | 维持上下文，但不把全部历史写死在前端 |

因此，Dify 知识库不是“网站的全部数据库”。Dify 保存的是可检索的教学文本索引；完整的视频、图片、二维码和资源元数据由网站数据库与 Blob 管理，网页服务端再用稳定 ID 关联它们。

### 2. 数据表如何设计

打开 [`prisma/schema.prisma`](../prisma/schema.prisma)，重点展示两个资源表：

```prisma
model ScienceKnowledgeItem {
  id        String @id
  baseId    String @map("base_id")
  category  String
  title     String
  ageLabel  String @default("")
  topic     String @default("")
  tags      String[] @default([])
  videoUrl  String @default("")
  body      String @default("") @db.Text
  resources ScienceKnowledgeResource[]
}

model ScienceKnowledgeResource {
  id              String @id
  resourceType    String
  knowledgeBaseId String
  title           String
  publicPath      String
  externalUrl     String
  isPublic        Boolean @default(true)
  sortOrder       Int @default(0)
}
```

讲解时要强调三个 ID：

- `LAB:EXP-...`、`LAB:STORY-...`、`LAB:POEM-...`：前端详情页的稳定条目 ID；
- `BASE:...`：同一资料的父级资源组 ID；
- `RESOURCE:...`：一张图片、一个视频或一个二维码的资源 ID。

有了这三个层次，系统才可以要求“步骤图片、视频和二维码必须属于同一 `BASE`”，避免模型将无关资源拼到当前教案下方。

### 3. 数据从原始资料到可检索资源的过程

建议用这张流程图：

```text
原始 Word / PDF / 图片 / 视频 / 二维码
                 │
                 ▼
人工清洗：标题、类别、年龄段、主题、来源、公开状态
                 │
                 ▼
src/data/science-knowledge.json（结构化源数据）
                 │
          ┌──────┴──────┐
          ▼             ▼
PostgreSQL 资源表    npm run export:dify
          │             │
          ▼             ▼
网页资源库        分类 Markdown 知识包 → Dify 知识库
```

现有资料包导出逻辑由 `npm run export:dify` 执行。当前代码中的源数据包有 172 条资源：科学诗 111 条、科学故事 28 条、科学实验 33 条。导出的 13 个 Markdown 会保留 `LAB`、`BASE`、`RESOURCE` 和公开媒体地址，便于模型回答时引用真实来源。

这里必须如实说明同步边界：仓库里较早的 Dify 配置说明仍记录过 163 条资料的线上状态，不能据此断言当前云端库已经同步为 172 条。正式授课前应重新执行导出、在 Dify 控制台检查 13 份文档是否都替换成功，并用一条资源检索问题做线上验收。

### 4. 本地检索为什么仍然存在

打开 [`src/lib/search.ts`](../src/lib/search.ts)。这里不依赖单一模型判断，而是做了：

- 中文关键词扩展；
- 同义词映射，例如“磁极、吸铁、磁性”补充为“磁力”；
- 2 至 6 字 n-gram 匹配；
- 年龄段、类型和主题优先级；
- 命中科学资源时优先走本地结构化目录，减少数据库往返；
- 园所资料、功能室、资格评估等再查询数据库的 `KnowledgeChunk`、`KnowledgeDocument` 和 `MediaAsset`。

这是 RAG 的工程化理解：检索不是让模型“凭感觉想起资料”，而是先拿到可追溯上下文，再让模型整理表达。

## 八、服务端智能体网关：60-75 分钟

### 1. 为什么必须有 `/api/ai-chat`

打开 [`app/api/ai-chat/route.ts`](../app/api/ai-chat/route.ts)。它是整个智能体的服务端网关，承担六件事：

1. 校验文字和附件；
2. 判断是否是闲聊、教案、图片识别、文档解析或封面生成；
3. 并行或按需检索本地资料；
4. 把问题、上下文和附件交给 Dify；
5. 将 Dify 的流式返回解析成前端可用的数据；
6. 模型不可用时返回基于资料库的回退结果，而不是空白页面。

核心原则：**模型 API 密钥只保留在服务端环境变量中。** 浏览器永远不直接调用 Dify、DeepSeek 或通义服务。

### 2. 附件与请求验证

该接口会区分 JSON 和 `multipart/form-data`，并对文件做白名单检查：

```ts
const MAX_ATTACHMENT_BYTES = 4 * 1024 * 1024;

const ATTACHMENT_MIME_BY_EXTENSION = new Map([
  [".jpg", "image/jpeg"],
  [".png", "image/png"],
  [".pdf", "application/pdf"],
  [".docx", "application/vnd.openxmlformats-officedocument.wordprocessingml.document"],
  [".pptx", "application/vnd.openxmlformats-officedocument.presentationml.presentation"],
]);
```

这段代码可以讲出四层意思：

- 不让无限大的文件占满 Serverless 函数；
- 不只信任浏览器提供的 MIME 类型，还核对扩展名；
- 视频不能直接送入当前视觉链路，必须先抽关键帧或整理文字；
- 上传失败时要告诉用户“附件未上传、请补充文字”，不能让模型假装看到了文件。

### 3. 路由与会话设计

接口中有一个很重要的判断：普通文字对话保留 Dify 的 `conversation_id`，图片、文档、完整教案和语音通话则启动独立会话。

```ts
const conversationId = voiceCall || attachment || hasImageAttachment || lessonPlanTitle(message)
  ? undefined
  : difyConversationId(body.conversationId);
```

原因是：视觉分析和文件分析需要以“当前附件”为唯一证据。如果把上一轮闲聊的上下文带进去，Dify 的问题分类器可能走错分支，或者把旧内容混入分析。

### 4. 后端先检索，再调用智能体

服务端会让本地检索与 Dify 调用配合，而不是二选一：

```text
用户问题
   ├─ 本地检索：找真实标题、图片、视频、二维码、LAB 详情入口
   └─ Dify：理解意图、从知识库取文段、生成适龄中文说明
                       │
                       ▼
服务端统一返回 reply + sources + photos + labLinks + agentResult + files
```

这也是为什么当 Dify 临时故障时，网站还能输出基础资料库结果；同时，返回值中的 `provider` 会标记为 `dify` 或 `fallback`，便于开发人员验收真实模型链路是否正常。

## 九、Dify、DeepSeek 与 RAG：75-93 分钟

### 1. Dify 在本项目中不是“一个模型”

Dify Cloud Chatflow 是工作流编排层。它负责：

- 接收来自网页服务端的 `query`、`user`、`conversation_id` 和可选文件；
- 对用户需求分类；
- 在合适的分支查询知识库；
- 把资料上下文放入模型系统提示词；
- 调用 DeepSeek、通义视觉或通义 AIGC 插件；
- 将最终文本、结构化 JSON 或生成文件返回网页。

### 2. 当前工作流的主要分支

投屏 Dify Chatflow 时，按以下顺序讲：

```text
用户输入
   │
   ▼
教学需求路由 / 问题分类器
   ├─ 教学设计
   ├─ 科学资源与媒体检索
   ├─ 上传文档解析
   ├─ 课件与文档创作
   ├─ 图片创作与配图
   ├─ 视觉实验分析
   ├─ 科学诗封面生成
   ├─ 实验复盘与改进
   └─ 科学作品反馈与探究任务
```

不要只说“智能体很聪明”。应解释：分类的目的是把不同类型任务交给合适节点，避免文字模型回答“我看到了图片”，或让图像模型承担文档排版。

### 3. DeepSeek 文本模型的职责

当前 Dify 教学设计、资源与媒体、文档审核等节点使用 `deepseek-v4-flash`。它适合：

- 将检索到的资料整理成中文回答；
- 生成完整教案和活动过程；
- 把文档正文改写为活动回顾、教研记录或课件大纲；
- 审核年龄段、材料、时间、安全提示和格式；
- 输出严格 JSON，用于网页渲染结构化卡片。

它不适合：直接读取未上传的图片、理解完整视频、凭空创造数据库中的资源链接。

**实现边界说明：** 仓库里存在 `src/lib/deepseek.ts` 这样的直连适配器，但当前生产聊天路由没有导入它。网页实际只使用 `src/lib/dify.ts` 中的 Dify API；DeepSeek 是 Dify 工作流内部配置的文本节点。因此课堂中应说“网站接入 Dify，Dify 再调用 DeepSeek”，不能说“浏览器或 Next.js 当前直接调用 DeepSeek API”。

### 4. RAG 的完整原理

可以用这一段话解释 RAG：

“大模型本身并不知道国科二幼资料库里有什么。RAG 的做法不是给模型重新训练一次，而是在用户提问时先检索相关资料，把找到的内容临时放进模型上下文，再要求模型基于这些证据回答。这样更新一份科学实验，只需更新数据库和知识包，不需要重新训练模型。”

本项目中，Dify 知识库采用按类别和年龄段整理的 Markdown；当前运行库使用适合中文关键词的倒排检索。网页服务端同时保留本地结构化检索，用于补足准确的资源关系和详情跳转。

当前本地检索也不是向量数据库检索：它使用关键词、别名、中文 n-gram 和 PostgreSQL 的包含查询。科学资源摘要与详情使用 Next.js 服务端短时缓存（约 60 秒），资源 API 还有 CDN 缓存策略；项目没有配置 Redis、Embedding 或 reranker。技术汇报时不要把这套实现说成“已上 Redis 缓存”或“已使用向量 RAG”。

### 5. 提示词应该怎样设计

把 Dify 系统提示词展示为四类约束，而不是长篇“角色扮演”：

```text
角色：你是服务幼儿园教师的科小贝。
依据：优先使用已检索资料；没有依据时说“资料库暂未收录”。
任务：按年龄段、活动时长、材料与安全边界生成可执行方案。
限制：不编造链接；不推断儿童身份、健康或能力；危险材料仅给教师安全替代方案。
输出：回答正文 + 可解析的 agent-result JSON（需要卡片时）。
```

这个提示词设计带来的工程价值是：同一份模型输出可以被前端稳定解析，而不是只依赖“看起来像 Markdown 的一段话”。

## 十、从 Dify API 到网页流式回复：93-102 分钟

打开 [`src/lib/dify.ts`](../src/lib/dify.ts)。它把 Dify API 调用封装为独立函数，避免前端组件直接处理鉴权和 SSE 格式。

### 1. 普通阻塞调用的核心请求

```ts
body: JSON.stringify({
  inputs: {},
  query: message,
  response_mode: "blocking",
  user,
  conversation_id: conversationId,
  files,
})
```

其中：

- `query` 是老师输入的问题；
- `user` 是服务端生成的匿名会话用户 ID；
- `conversation_id` 是 Dify 返回的多轮会话标识；
- `files` 是先上传到 Dify 后得到的文件引用；
- `response_mode` 选择阻塞或流式。

### 2. 为什么聊天必须使用 SSE 流

教案生成、视觉分析和图片生成会比一句普通回答慢得多。如果页面一直空白，老师会误以为系统失效。项目通过 Server-Sent Events（SSE）将状态逐段推给网页：

```text
Dify SSE 事件
    ↓ parseDifyStream
Next.js 服务端重新封装为
    meta    返回资料来源、图片、详情入口
    status  显示“图片正在识别”或“教案正在生成”
    delta   普通文本逐字/逐段显示
    done    最终回答、会话 ID、文件、结构化结果
    error   受控错误信息
    ↓
SciencePet.tsx 更新消息气泡
```

`app/api/ai-chat/route.ts` 对不同任务设置了不同等待预算，例如普通回答更短，完整教案和图片识别更长。这样既不让普通聊天长期等待，也不给长任务过早套用泛化模板。

### 3. 为什么需要回退结果

模型服务可能发生 API 认证失败、工作流未发布、额度不足、网络超时或插件故障。项目不能把“调用失败”伪装成模型成功，因此：

- 一般资料查询可使用本地检索结果生成 `fallback`；
- 图片识别没有真实视觉证据时，只能说明无法分析并要求补图，不能编造观察；
- 图像生成没有返回图片文件时，返回可重试错误和默认占位封面，不能显示“已生成”；
- `provider` 字段可用于运维检查实际是否走到 Dify。

## 十一、视觉模型：图片识别为何不能直接交给 DeepSeek：102-114 分钟

### 1. 模型分工

| 任务 | 进入的模型或节点 | 输出边界 |
|---|---|---|
| 普通对话、教案、文档 | DeepSeek 文本节点 | 基于文字和检索上下文写作 |
| 实验图片识别 | 通义 `qvq-max` 视觉节点 | 只写图片中可见材料、操作、现象、风险和证据缺口 |
| 视觉结论整理 | DeepSeek 文本节点 | 将可见证据整理为教师建议，不能把猜测说成事实 |
| 科学诗封面 | 通义 AIGC `qwen-image-2.0-pro` | 返回一张无文字插画文件 |

### 2. 图片上传的实际链路

```text
浏览器选择图片
  ↓
SciencePet.tsx 压缩/预览并使用 FormData 上传
  ↓
/api/ai-chat 验证扩展名、MIME、大小和图片类型
  ↓
src/lib/dify.ts 调用 /v1/files/upload 得到 upload_file_id
  ↓
调用 Dify chat-messages，files=[{ type:"image", transfer_method:"local_file", upload_file_id }]
  ↓
Dify 路由到 qvq-max 视觉实验分析节点
  ↓
DeepSeek 整理为 vision_observation
  ↓
服务端 parseAgentResult → AgentResultCard.tsx
```

`app/api/ai-chat/route.ts` 会明确给 Dify 添加路由指令：检测到图片时进入“视觉实验分析”分支，不能走普通文本聊天；同时不复用旧会话编号，防止旧上下文把分类器带偏。

### 3. 结构化视觉结果

视觉结果用 `agent-result` 围栏返回 JSON，典型字段如下：

```json
{
  "kind": "vision_observation",
  "facts": ["图片中直接可见的材料或操作"],
  "judgements": ["必须标为推测/待验证的判断"],
  "missing_evidence": ["遮挡、模糊或缺少的关键证据"],
  "actions": ["教师下一步可执行的建议"],
  "safety": ["安全提醒"],
  "confidence": 0.82
}
```

为什么要分字段：网页可以把“事实”“待确认”“安全”用不同区域展示，教师也更容易判断哪些信息能直接使用，哪些需要补拍或复核。

### 4. 视觉链路的验收原则

现场可以这样提问听众：“如果图片里只有材料，没有操作过程，模型能不能说实验已经成功？”正确答案是不能。合格输出必须说明“可见什么”和“缺少什么”，而不是用常识补全画面外内容。

## 十二、图像生成与封面持久化：114-120 分钟

科学诗封面生成不是“得到一段图片描述”就完成了，完整链路包括：生成、获得真实文件、持久化文件、更新资源条目。

```text
老师新增科学诗，填写标题、主题和正文
   ↓
POST /api/science-resources/generate-cover
   ↓
服务端构造安全的无文字插画提示词
   ↓
Dify → 通义 AIGC 插件 → qwen-image-2.0-pro
   ↓
Dify 返回图片文件或公开图片 URL
   ↓
服务端验证结果，下载图片并存入阿里云 OSS
   ↓
PostgreSQL 事务：替换该科学诗的“封面”资源并更新 imageCount
   ↓
资源库刷新后显示新封面
```

打开 [`app/api/science-resources/generate-cover/route.ts`](../app/api/science-resources/generate-cover/route.ts) 和 [`src/lib/science-cover-sync.ts`](../src/lib/science-cover-sync.ts)。必须讲出两个工程细节：

1. Dify 返回的文件地址可能是临时地址，不能直接永久写入资源库；项目会把它复制到阿里云 OSS，再通过网站媒体接口提供受控访问。
2. 更新封面使用数据库事务：先删除同一 `baseId` 下旧的封面资源，再写入新资源，同时重新计算图片数量，避免页面出现多个“当前封面”。

## 十三、文件上传、资源新增与 Word 下载：120-123 分钟

### 1. 大文件为什么不直接经过网页服务器

`app/api/science-resources/upload/route.ts` 由网站服务端接收上传文件并写入阿里云私有 OSS，同时限制：

- 路径必须以 `science-resources/` 开头；
- 文件类型必须在白名单；
- 最大文件大小为 100MB；
- 上传频率通过 `checkPublicRateLimit` 控制。

对象存储凭证只在服务端使用，不会下发到浏览器。

### 2. Word 教案为什么可以下载

有两层策略：

1. Dify 的文档分支若返回真实 DOCX/PDF/PPTX/XLSX 文件，服务端只接受受控来源并生成下载入口；
2. 如果 Dify 没有返回 Word，前端使用 [`src/lib/lesson-plan-docx.ts`](../src/lib/lesson-plan-docx.ts) 解析教案 Markdown，并用 JSZip 组装 DOCX 的 Open XML 文件作为兜底。

这份 DOCX 生成代码按园所示例教案的表格结构拆分“活动目标、准备、过程、备注、反思”等字段，说明“模型负责内容，程序负责格式”。

必须明确：

- 不在截图、PPT、GitHub 提交、聊天记录或 Dify 知识库中展示真实密钥；
- 环境变量修改后，需要重启 ECS 上的网站服务使配置生效。

### 3. 将新版本发布到阿里云 ECS

```text
本地修改代码
   ↓
git add / git commit / git push
   ↓
GitHub 仓库产生经审核的新提交
   ↓
发布机准备代码快照并传到阿里云 ECS
   ↓
安装依赖 → 执行预处理 → next build
   ↓
生成 standalone 产物，由 systemd 启动 Next.js 常驻服务
   ↓
通过 Nginx 提供 HTTPS，线上验证接口和媒体资源
```

项目的 `package.json` 中，`build` 是 `next build`，而 `prebuild` 会调用科学资源与评估资料的预处理脚本。是否写入数据库受 `SEED_SCIENCE_ON_BUILD`、`SEED_QUALIFICATION_REPORT_ON_BUILD` 等开关控制；发布前仍要确认目标环境的变量，避免不经审查地覆盖正式资料。

### 4. ECS 上的 Next.js 常驻服务

本项目在 ECS 上通过 systemd 运行 Next.js standalone 服务，Nginx 转发公网请求。因此：

- 服务进程重启后仍需从数据库恢复业务状态；
- 多轮对话依赖 `conversation_id`，业务数据依赖 PostgreSQL；
- 用户媒体写入 OSS，不依赖临时构建目录；
- 长任务需要流式响应和 Nginx/Node.js 超时配置；
- 运维时通过 systemd 检查和重启应用，并检查服务日志。

### 2. 常见故障的定位顺序

**问题：网页能打开，但智能体没有回答。**  
检查浏览器网络请求 `/api/ai-chat`，再检查 ECS 服务日志（`journalctl -u guoke-web`）；确认模型服务配置、Dify 工作流发布状态和账单/额度。不要只根据页面看到 `fallback` 就认定上游服务已正常。

**问题：有回答，但资源链接不对。**  
先查 `search.ts` 命中的 `LAB/BASE/RESOURCE`，再查数据库的资源关系；修复数据，不要用提示词强行让模型“猜正确链接”。

**问题：图片识别无结果。**  
确认浏览器实际上传了图片、`/v1/files/upload` 成功返回文件 ID、Dify 路由进入 qvq-max 节点、结构化输出没有只返回占位 JSON。上传完整视频不是当前支持路径，应改用关键帧。

**问题：科学诗生成了，但封面没有更新。**  
检查图像服务是否返回文件、文件 URL 是否可下载、OSS 服务端凭证是否有效、`persistScienceCoverImage` 是否成功、数据库是否只保留一个封面资源。

**问题：教案生成很慢或一直加载。**  
检查模型文档分支、输出工具和 Node.js/Nginx 超时；长教案应走流式状态反馈。若模型没有返回文件，确认浏览器端 DOCX 兜底是否被触发。

## 十八、专家答疑口径（主讲结束后的备用内容）

**问：这是直接调用 DeepSeek API 吗？**  
答：网页不直接调用。网页调用自己的 Next.js 服务端 API，服务端再调用 Dify Chatflow；Dify 根据工作流选择 DeepSeek、通义视觉或通义图像生成节点。这样密钥不暴露，流程也可以调整。

**问：Dify 既然有知识库，为什么还要数据库？**  
答：知识库擅长为模型提供文本上下文，数据库擅长保存结构化业务关系、权限、图片、视频、二维码和稳定 ID。两者职责不同，不能互相替代。

**问：为什么图片识别不能总用 DeepSeek？**  
答：当前文本模型节点负责文本推理与写作；图片需要带视觉输入能力的 qvq-max 节点。视觉节点输出可见证据后，文本模型再组织成教育语言，这是更可靠的分工。

**问：模型回答错误怎么办？**  
答：第一步看有没有检索到正确资料；第二步看提示词是否要求“无依据不编造”；第三步看结构化输出是否把事实和推测分开；最后由教师审核。不要把错误完全归因于模型“聪明或不聪明”。

**问：网站上是不是保存了所有老师的对话？**  
答：当前多轮上下文主要通过 Dify `conversation_id` 维护；是否持久化业务会话要以具体功能的数据库实现和隐私策略为准。生产环境应明确保存范围、保留期限和访问权限。

**问：能不能分析任意视频？**  
答：当前链路不能直接理解完整视频。应上传关键帧或提供文字记录，然后进入视觉或复盘分支。
